# RFC E5: runner and engine

Owner: E5. Each item is a request to the architect or to the named owner. E5 uses a local adapter meanwhile, so nothing here blocks the build.

## 1. Give the agents clock its schedule (plugin/container.ts, E1)

What: `createAgentsClock` takes an optional `schedule()` and `log`. Without them the clock uses the defaults (idle after 120 s, nightly off, no busy deferral), so the settings `agents.idleStartSec`, `agents.onlyWhenIdle` and `agents.nightly` have no effect until the container passes them.

Why: the clock decides when to ask the runner to organise; the interval, hour and idle rules are settings, and a change must apply at the next tick without recreating the clock.

```ts
// container.ts, in the createAgentsClock({...}) call
schedule: () => {
  const a = settings.value.agents;
  return { onlyWhenIdle: a.onlyWhenIdle, idleStartSec: a.idleStartSec, nightly: a.nightly, deferWhileBusyMs: 0 };
},
log: log.child("clock"),
```

`deferWhileBusyMs` stays 0 until a setting for "wait while Claude Code is busy" exists (CORTEX-UX §12 lists none); the clock already honours a non-zero value.

## 2. `ImportArgs.importChanged` (shared/protocol/runner.ts, architect)

What: E3's RFC §4. The runner already forwards `importChanged` from the request into `ctx.options.importChanged` for the `raw` importer, reading it through a cast until the field exists.

```ts
export interface ImportArgs {
  // ...existing members
  /** Import the new version of raw documents that changed on disk: all of them, or these vault paths. */
  importChanged?: boolean | string[];
}
```

## 3. Declare what the scheduler adds to `JobContext` (agents/jobs.ts, E6)

What: `agents/scheduler.ts` builds `SchedulerJobContext = JobContext & JobContextExtras` (`origin`, `settingsSource`, `pluginVersion`, `deadline?`, `promptVersions`). E6's `runJob` reads them from the context through a cast.

```ts
export interface JobContext {
  // ...existing members
  origin: "plugin" | "skill";
  settingsSource: "plugin" | "data.json" | "defaults";
  pluginVersion: string;
  deadline?: number;
  promptVersions: Readonly<Record<JobKind, string>>;
}
```

## 4. Node-free typing of the plugin tier (tsconfig.browser.json, architect)

What: `ui/` imports the `RunnerClient` type from `plugin/runnerClient.ts`, so the browser program type-checks that file without `@types/node`. `runnerClient.ts` therefore reaches Node (child_process, fs, path, require) only through the host's `require` behind small local types, and finds Node 20+ and kills the child tree with its own short helpers instead of importing `node/platform.ts` and `node/spawn.ts` (which the browser program cannot check).

Why this matters: if the architect later adds Node types to the browser program for `src/plugin/**`, the helpers in `runnerClient.ts` can be replaced by `findNode` and `killTree` from `src/node/` (one import each). Until then nothing is needed.
