# RFC E8: layout worker contract changes for the standing figure

Owner: E8 (layout worker). Reader: the architect. Status: proposed. Every item has a local adapter in E8's files, so nothing is blocked.

## 1. Haze kinds follow the standing anatomy (CORTEX-UX §12.19.6)

**What.** `src/shared/protocol/worker.ts` still lists the lying figure's kinds (`body`, `vertebra`). The standing figure has no filled body haze and no vertebra chevrons. It has nerve guides and twigs, a bright cord thread and segment rings.

**Why.** The renderer gives each kind its own intensity (guides 0.24 → 0.13, twigs 0.16, cord thread 0.95, rings 0.20). With the old kinds the cord thread and the rings share `vertebra`, and the guides and twigs share `body`, so the thread is drawn too dim or the rings too bright.

**Exact TypeScript.**

```ts
export type HazeKind = "brain" | "nerve" | "thread" | "ring" | "brainstem" | "undated";
export const HAZE_KINDS: readonly HazeKind[] = ["brain", "nerve", "thread", "ring", "brainstem", "undated"];
```

**Adapter meanwhile.** `anatomy.ts` produces the fine kinds (`HAZE_SUBS`: brainFolds, brainVolume, cerebellum, brainLips, nerve, twig, thread, ring, brainstem) in `AnatomyModel.haze.sub` and maps them to the old protocol kinds with `HAZE_PROTOCOL_KIND` (nerve and twig → `body`, thread and ring → `vertebra`). When the contract lands, `HAZE_PROTOCOL_KIND` becomes the identity on `nerve | thread | ring` and the placement result copies `kind` from the new table. The renderer should read per-kind intensities from §6.5; the brain sub-kinds (folds 0.80, lips 0.55, volume 0.12, cerebellum 0.50) need `brain` split further, or the renderer derives them from position. Say which you prefer.

## 2. Default pose is Standing (CORTEX-UX §12.19.1)

**What.** `DEFAULT_SETTINGS.general.pose` becomes `"standing"`; add `general.poseChosen: boolean` (false by default) and bump `SETTINGS_VERSION` with a migration so a stored `"lying"` from an older build reads as Standing until the person picks a pose. `src/state/types.ts` line 87: `settings?.general.pose ?? "standing"`.

**E8 adapter.** `resolvePose(undefined)` returns `DEFAULT_SETTINGS.general.pose`. Nothing in E8 hard-codes a pose, and the tests compare against `DEFAULT_SETTINGS`, so they pass before and after the change. Today the shared default is still `"lying"`, so a view that sends no pose is laid out Lying. Views always send `PlacementParams.pose`.

## 3. Optional placement input: area slots (already read by `placement.ts`)

**What.** Wedges run in the sticky slot order of the area dimension.

```ts
export interface PlacementParams {
  // …existing fields
  /** colours.json `space` slots; territories run in slot order (CORTEX-UX §6.3). */
  areaSlots?: Readonly<Record<string, number>>;
}
```

**Adapter.** `placement.ts` reads it through `PlacementExtras` and ignores it when absent.

## 4. Colour slots need the vault and cache paths (container, E1)

**What.** `createColourSlotService(deps?)` persists `.vault-meta/cortex/state/colours.json` atomically under the `state:colours` lock, re-reading inside the lock so two computers converge. The container calls it without arguments, so today the slots live in memory only.

```ts
colours: createColourSlotService({ vaultRoot: bg.vaultRoot, cacheDir: bg.cacheDir, log: bg.log.child("colours") }),
// and once at start: await services.colours.load?.();
```

**Adapter.** With no `deps` the service keeps slots in memory.

## 5. Selection source lines use the standing control point (E7, `indexOps.ts`)

**What.** CORTEX-UX §12.19.7: source lines pass outside the torso and never cross the cord. `indexOps.addCurve` lifts the control point away from the figure's long axis, which for the standing figure crosses the torso. `lines.ts` exports the standing rule:

```ts
export function sourceControl(from: Vec3, to: Vec3, fallbackSide: number, out?: Vec3): Vec3; // skeleton frame
```

`indexOps` should unpose the view's positions (`unposeXYZ`), call `sourceControl(entryPosition, notePosition, side)` for the control point, and pose the result. The global lines (`computeLines`) already do this.

## 6. Camera numbers (E10, `render/tuning.ts`)

E8's `FIGURE.camera` is the worker's copy of the §6.8 numbers: heading 154° from the frontal pole toward the figure's right, elevation 9°, target (0, 0.3, −0.2), field of view 30°, spin 60 s per turn, sway ±26° over 40 s, crown fraction 0.09, bottom inset 68 px, slide 6 px steps up to 36 px. `render/` may not import `worker/`, so `tuning.ts` keeps its own copy; the two must agree. `homeDirection(pose)` and `standingFrame()` are exported for tests only.
